# How USDM artifacts are produced for a new version: USDM 4.1.0

Date: 2026-11-19

This document explains how a new version of the USDM deliverables is created in this repository, and applies it to
USDM 4.1.0 on branch `release-4-1-0`. It is based on:

- the only project workflow, `.github/workflows/diff-and-data-dict.yml`
- the generator it runs, [`cdisc-org/DDF-RA-Tools`](https://github.com/cdisc-org/DDF-RA-Tools) (`main.py` and
  `ddf_ra_tools/parsers/ct_parser.py`, read at commit `573e532`)
- the commit history of the 4.0.0 release (`main`, tagged `v4.0.0` at `aa303cb`)

Where a step is inferred from history rather than written down in the repository, it says so.

## 1. The artifacts and how they relate

Three artifacts are maintained by hand. Everything else is either generated from them by CI or curated by hand from
the generated output.

```text
 Hand-maintained (source of truth)              Generated by CI (DDF-RA-Tools)           Hand-curated afterwards
 ─────────────────────────────────              ──────────────────────────────           ───────────────────────
 USDM_UML.qea ──(EA export)──> USDM_UML.xmi ─┐   UML_DELTA_<prev>_<curr>.csv              CT_DELTA_*.xlsx
                               UML_Views/*.png│   API_DELTA_<prev>_<curr>.csv              USDM_CT_Changes.xlsx
 USDM_API.json  (+ USDM_API.yaml, kept in sync)├─> CT_DELTA_<prev>_<curr>.csv               USDM_CORE_Rules(.xlsx, _Changes)
 USDM_CT.xlsx ───────────────────────────────┘   dataDictionary.MD                        Documents/Examples/*.json
                                                  dataStructure.yml                        Documents/Mappings/*.xlsx
                                                  alignment.csv                            Informative model diagram
                                                  CORE Test Data Template.xlsx             USDM-IG.pdf
```

Key points:

- **The generator reads `USDM_UML.xmi`, never `USDM_UML.qea`.** A model change made in Enterprise Architect has no
  effect on any generated file until the XMI is re-exported and committed.
- **The generator reads `USDM_API.json`, never the YAML.** `USDM_API.yaml` must be kept in sync by hand. In 4.0.0 both
  were edited in the same commit (`4f73979`, "Update API version and endpoints to v4").
- **The CT parser reads only the `DDF Entities&Attributes` sheet** of `USDM_CT.xlsx`, matching columns by their
  header names (`Entity Name`, `Role`, `Inherited From`, `Logical Data Model Name`, `NCI C-code`,
  `CT Item Preferred Name`, `Definition`, `Has Value List`, `Codelist URL`).
- `alignment.csv` compares cardinality and characteristics across UML, API and CT. A release is consistent when it
  contains only the header row.

## 2. The CI workflow: "Generate Diff and Data Dict"

### 2.1 When it runs

| Trigger | Condition |
| -- | -- |
| `push` | Any branch **except `main`**, and only when the push changes `Deliverables/UML/USDM_UML.xmi`, `Deliverables/CT/USDM_CT.xlsx` or `Deliverables/API/USDM_API.json` |
| `workflow_dispatch` | Manual run, with input `prev-branch` (the branch or tag to compare against; default `main`) |

Changes to the `.qea`, the YAML, the PNGs, the rules or the examples **do not trigger it**.

### 2.2 What it does

1. Checks out the current branch to `currRelease/` and the previous release (`prev-branch`, default `main`) to
   `prevRelease/`.
2. Checks out DDF-RA-Tools, installs Python 3.12 and its `requirements.txt`, and installs `xmlstarlet`.
3. Reads four version numbers and turns dots into hyphens:

   | Variable | Source |
   | -- | -- |
   | `PREVIOUS_VERSION` | `info.version` in the previous branch's `USDM_API.json` |
   | `CURRENT_VERSION` | Branch name with `release-` removed |
   | `CURRENT_API_VERSION` | `info.version` in this branch's `USDM_API.json` |
   | `CURRENT_UML_VERSION` | `project/@version` of the diagram named `USDM` (type `Logical`) in `USDM_UML.xmi` |

4. **Fails** unless all of these hold:
   - every value was found and contains a hyphen
   - `PREVIOUS_VERSION` ≠ `CURRENT_VERSION`
   - `CURRENT_API_VERSION` = `CURRENT_VERSION`
   - `CURRENT_VERSION` starts with `CURRENT_UML_VERSION`
5. Copies the XMI, CT workbook and API JSON from both checkouts into `DDF-RA-Tools/resources/{prevRelease,currRelease}/`
   and runs `python3 ./main.py`, which does the following in order:
   1. UML delta: previous XMI vs current XMI
   2. API delta: previous JSON vs current JSON
   3. CT delta: previous CT vs current CT
   4. Combines current UML, CT and API into one model and writes `dataStructure.yml`, `dataDictionary.MD`,
      `alignment.csv` and `CORE Test Data Template.xlsx`
6. Copies the outputs back into the branch, renaming the deltas to `*_DELTA_<PREVIOUS_VERSION>_<CURRENT_VERSION>.csv`.
7. Commits everything (`git add .`) as `github-actions` with the message **"Generate Diff and Data Dict"** and pushes
   to the same branch.

### 2.3 Values for 4.1.0

| Variable | Required value | Value on `release-4-1-0` today |
| -- | -- | -- |
| `PREVIOUS_VERSION` (from `main`) | `4-0-0` | `4-0-0` ✅ |
| `CURRENT_VERSION` (branch name) | `4-1-0` | `4-1-0` ✅ |
| `CURRENT_API_VERSION` | `4-1-0` | `4-0-0` ❌ |
| `CURRENT_UML_VERSION` | `4-1-0` (or a prefix such as `4-1`) | `4-0-0` ❌ |

The workflow will fail on the next qualifying push until `info.version` in the API and the `USDM` diagram version in
the XMI are both set to 4.1.0.

Files the workflow will produce for 4.1.0:

- `Deliverables/UML/UML_DELTA_4-0-0_4-1-0.csv`
- `Deliverables/API/API_DELTA_4-0-0_4-1-0.csv`
- `Deliverables/CT/CT_DELTA_4-0-0_4-1-0.csv`
- `Deliverables/UML/dataDictionary.MD`, `dataStructure.yml`, `alignment.csv`
- `Documents/CORE Test Data Template/CORE Test Data Template.xlsx`

## 3. Step-by-step process for 4.1.0

The order follows how 4.0.0 was produced (commits `4f73979` through `aa303cb`).

### Step 1: Release branch

Work on `release-4-1-0`, created from `main`. This already exists. Feature work can be done on topic branches and
merged into it, as with PR #719 (`dev-4-1-0-Edwin`). PRs target the release branch, not `main`.

### Step 2: Set the version numbers

Do this before, or in the same push as, the first model change, so CI does not fail:

| Where | Change |
| -- | -- |
| `Deliverables/API/USDM_API.json` | `info.version`: `4.0.0` → `4.1.0` |
| `Deliverables/API/USDM_API.yaml` | `info.version`: `4.0.0` → `4.1.0` |
| UML `USDM` diagram (in EA) | Version → `4.1.0`, then re-export the XMI |

The API paths stay `/v4/...`; the 4.0.0 release changed them only because the major version changed.

### Step 3: Make the model change in all three artifacts

For each ticket:

1. **UML**: edit `USDM_UML.qea` in Enterprise Architect, then:
   - export `USDM_UML.xmi`
   - re-export `USDM_UML.png` and the affected `UML_Views/*.png`
   - commit the `.qea`, `.xmi` and PNGs together (the 4.0.0 commit `131fcdf` committed XMI and PNGs together)
2. **API**: edit `USDM_API.json` and make the same edit in `USDM_API.yaml`. Each class has an `-Input` and an
   `-Output` schema, and both must change.
3. **CT**: edit the `DDF Entities&Attributes` sheet of `USDM_CT.xlsx` (entity, attribute and relationship rows, with
   C-codes and definitions), add any new value sets to `DDF valid value sets`, and log the change in
   `USDM_CT_Changes.xlsx`.
   - The parser attaches each attribute row to an entity it has **already read**. An attribute row that comes before
     its entity's `Entity` row, or whose `Entity Name` has no `Entity` row, will crash the generator (`KeyError`).
   - `Has Value List` is parsed as `Y (<codelist>)` to extract the codelist reference; use that exact form.

### Step 4: Push, let CI generate, then pull

1. Push to `release-4-1-0`.
2. Wait for the workflow to finish; it pushes a "Generate Diff and Data Dict" commit to the branch.
3. `git pull` before doing more work, or the next push will be rejected.
4. Check `Deliverables/UML/alignment.csv`. Any row other than the header is a mismatch between UML, API and CT. Fix it
   in the source artifacts and push again. The 4.0.0 history shows this loop running many times (10 CI commits between
   2025-05-01 and 2025-05-28).

Don't edit the generated files by hand. The next CI run overwrites them.

### Step 5: Update the CORE rules

Update `Deliverables/RULES/USDM_CORE_Rules.xlsx` for the new or changed model elements. Record each change on a new
sheet of `USDM_CORE_Rules_Changes.xlsx` (for example "Changes release 4.0 -> 4.1"), following the existing sheet
layout. In 4.0.0 this was done near the end (`2ab9587`, "Updated CORE rules with last changes for v4").

### Step 6: Hand-curated companions

Done in this order for 4.0.0:

| Artifact | 4.0.0 commit | What to do for 4.1.0 |
| -- | -- | -- |
| `CT_DELTA_*.xlsx` | `ddb59ed` | Optional: build `CT_DELTA_4-0-0_4-1-0.xlsx` from the generated CSV with terminology changes noted |
| Delta READMEs | `ade46ea` | Check that `*_DELTA_README.md` still describe the columns correctly |
| Informative model diagram | `800e915` | Update `Documents/DDF USDM Model Informative.graffle` / `.png` / `.pdf` in OmniGraffle |
| Example study files | `d63b666` | Update all 5 JSON files under `Documents/Examples/`, including `usdmVersion` (currently `4.0.0` in all five) |
| Mapping workbooks | `728f02d` | Update `Documents/Mappings/*.xlsx` for new attributes and the version |
| Implementation Guide | `aa303cb` | Publish the updated `Deliverables/IG/USDM-IG.pdf` |

### Step 7: Publish

`main` has a linear history with no release merge commits, and tag `v4.0.0` points at the final release commit
(`aa303cb`). This suggests that the release branch was fast-forwarded into `main` and tagged (inferred; it isn't
documented in the repository). For 4.1.0:

1. Bring `release-4-1-0` into `main`.
2. Tag the result `v4.1.0`.

Pushes to `main` don't trigger CI, so all generated files must be final on the release branch first.

## 4. Other ways to run the generator

### 4.1 Compare against a different baseline (manual run)

For 4.0.0 the team also published cumulative 3.0.0 → 4.0.0 deltas (`47a260e`). To do the same:

- Trigger the workflow manually on `release-4-1-0` (Actions → "Generate Diff and Data Dict" → Run workflow) and set
  `prev-branch` to the baseline tag, for example `v4.0.0` or `v3.0.0`.
- `CURRENT_VERSION` comes from the branch the run is started on, so start it on `release-4-1-0`.
- The output is named after the baseline's API version (for example `*_DELTA_3-0-0_4-1-0.csv`).

### 4.2 Run the workflow locally

From the workflow file:

```bash
gh act workflow_dispatch -P ubuntu-latest=catthehacker/ubuntu:act-latest --secret-file ../DDF-RA-Actions/my.secrets
```

This needs Docker and the secrets file from the separate DDF-RA-Actions checkout.

### 4.3 Run DDF-RA-Tools directly

Steps 5 and 6 of the workflow, done by hand (useful to check `alignment.csv` before pushing):

```bash
git clone https://github.com/cdisc-org/DDF-RA-Tools.git && cd DDF-RA-Tools
pip install -r requirements.txt
mkdir -p resources/prevRelease resources/currRelease
# previous release (main) inputs
git -C ../DDF-RA show main:Deliverables/UML/USDM_UML.xmi   > resources/prevRelease/USDM_UML.xmi
git -C ../DDF-RA show main:Deliverables/CT/USDM_CT.xlsx    > resources/prevRelease/USDM_CT.xlsx
git -C ../DDF-RA show main:Deliverables/API/USDM_API.json  > resources/prevRelease/USDM_API.json
# current release inputs
cp ../DDF-RA/Deliverables/UML/USDM_UML.xmi  resources/currRelease/
cp ../DDF-RA/Deliverables/CT/USDM_CT.xlsx   resources/currRelease/
cp ../DDF-RA/Deliverables/API/USDM_API.json resources/currRelease/
python3 main.py
# outputs: UML_DELTA.csv, API_DELTA.csv, CT_DELTA.csv, dataDictionary.MD, dataStructure.yml,
#          alignment.csv, "CORE Test Data Template.xlsx"
```

This skips the version checks, so also confirm the versions with the commands in `CLAUDE.md`.

## 6. Things that commonly go wrong

- **CI never runs:** only the `.qea` was committed. Export and commit the XMI.
- **CI fails the version check:** the branch name, API `info.version` and XMI diagram version disagree (section 2.3).
- **Push rejected after CI:** CI pushed its own commit. Pull and push again.
- **Generator crash in the CT step:** an attribute row in `DDF Entities&Attributes` appears before its entity's
  `Entity` row, or uses an entity name with no `Entity` row.
- **YAML out of date:** nothing checks it. Compare `info.version` and schema names in the JSON and YAML before release.
- **`alignment.csv` not empty:** a cardinality or type differs between UML, API and CT, or an element exists in only
  one or two of them.
