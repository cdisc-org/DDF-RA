2. M11 mapping review workbook

Documents/M11/m11_mapping_review.xlsx is derived from the published Documents/Mappings/m11_mapping.xlsx. A cell-by-cell comparison of the 18 shared mapping columns (A–R, 325 rows) found no differences. Both workbooks target USDM v4.0.0 and the M11 "Updated Step 2 Draft, 14th March 2025".

What was added

  • A "Review Comments" column group (S–V) on the Mapping sheet.
  • S, T and U are formulas (=Cn, =In, =Jn) that repeat the M11 Element Name, USDM Class and USDM Attribute beside the comment cell.
  • V is a free-text Comment column. It is empty in all 323 data rows: no review feedback has been captured yet.
  • The Readme sheet gains a "Review Columns" section that defines Comment = Reviewer comments.

Mapping coverage (323 M11 elements)

  • 322 Mapped, 1 Not Mapped (1.1.2 Overall Design, "Not applicable").
  • 160 elements map to NarrativeContentItem.text.
  • 129 numbered M11 sections are covered, plus the un-numbered Title Page.
  • 3 rows have no Mapping Category, for example Title Page / Proprietary Name(s), which also has no Section Number.

Observations & recommendations

AttentionBranch name suggests a 4.0.1 release, but nothing normative has changed

USDM_API.json is still info.version 4.0.0, and the UML, CT, rules and IG are unchanged. Merging as-is would not produce a USDM 4.0.1. If a 4.0.1 patch is intended, the normative changes and version bumps still have to be made. Making them will also trigger the "Generate Diff and Data Dict" workflow, which requires the branch version to match the API info.version. Otherwise, consider merging this content as informative documentation without tying it to a release.

Update, 20 November 2026: release-4-1-0 is now the active release branch, so a separate 4.0.1 patch is unlikely to be needed. The simplest path is to carry this M11 material into 4.1 (see the next finding) and retire release-4-0-1 without publishing a 4.0.1.

AttentionThe M11 material is not on release-4-1-0 (added 20 November 2026)

release-4-1-0 (c69fd36, 10 November 2026) also branches from main and is 8 commits ahead of it, but it doesn't contain any of the 5 commits on release-4-0-1. Unless they're brought across, USDM 4.1 will ship without the M11 review folder or the updated Documents/README.md.

A trial merge (git merge-tree) of release-4-0-1 into release-4-1-0 completes without conflicts. release-4-1-0 changes only CLAUDE.md, the CORE rules workbooks and the UML files under Deliverables/, none of which this branch touches. Merging release-4-0-1 into release-4-1-0, through a PR against the release branch, is therefore low-risk. It doesn't change USDM_UML.xmi, USDM_CT.xlsx or USDM_API.json, so it doesn't trigger the CI workflow. Address the stale model copy (below) at the same time.

AttentionVersion labels conflict within the M11 package

The class-map PDF is labelled USDM V3.13 and M11 Template Specification dated 13th March 2025. The review workbook states USDM v4.0.0 and M11 Updated Step 2 Draft, 14th March 2025. Align these labels before the package is circulated for external review.

AttentionSecond copy of the EA model has already drifted

Documents/M11/USDM_UML.qea duplicates the 2.3 MB canonical model only to hold one extra diagram. Any later model change in Deliverables/UML/ leaves this copy stale. Consider adding the "M11" diagram to Deliverables/UML/USDM_UML.qea and keeping only the PNG export under Documents/M11/. The commit message says the copy is temporary ("for the moment").

Update, 20 November 2026: this has now happened. The copy's model content is identical to the published 4.0 model, but the canonical model on release-4-1-0 has since changed (PR #719, UGG-57/61). The copy lacks:

  • the new class InterventionAssignment;
  • InterventionalStudyDesign.controlType (Code, 1);
  • the association InterventionalStudyDesign.interventionAssignment (1).

This affects M11 directly:

  • The diagram: InterventionalStudyDesign is on the "M11" diagram, so the diagram shows it without its two new 4.1 properties.
  • The mapping: the 4.1 change models M11 content that the mapping currently places elsewhere.
    • The M11 element Control type (1.1.2) is mapped to StudyArm.type.
    • Intervention assignment method and randomly assigned to trial intervention/enrolled (1.1.2), and Method of Assignment to Trial Intervention (4.1), are mapped to StudyDesign.characteristics.
    In 4.1 these have dedicated homes, InterventionalStudyDesign.controlType and InterventionAssignment, so those mapping rows will need re-pointing in both the review workbook and the published Documents/Mappings/m11_mapping.xlsx.

Merging the copy into 4.1 as it stands would ship two different versions of the model. Before merging into release-4-1-0:

  • move the "M11" diagram into the canonical .qea (or recreate it there), adding InterventionAssignment, and drop the copy;
  • re-export M11.png;
  • update the four mapping rows above.

The one unmapped element and the three uncategorised rows exist in both the published and review workbooks, so they are not regressions.

Method

The comparison used git fetch origin, then git log and git diff --stat between main (aa303cb) and origin/release-4-0-1 (a5049a1), with merge-base aa303cb. The Excel workbooks were compared cell by cell with openpyxl. The two Enterprise Architect .qea files (SQLite) were compared by row counts per table and by a full SQL dump diff. Diagram images were rendered from the branch's PNG and PDF files.
